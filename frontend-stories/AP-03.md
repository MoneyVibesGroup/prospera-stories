## User Story

En tant qu'**administrateur plateforme Money Vibes**,
je veux **traiter la file des dossiers KYC en attente : consulter les pièces (RCCM/CFE) et approuver ou rejeter avec motif**,
afin d'**activer les organisations légitimes et écarter les dossiers non conformes**.

---

## Contexte

Maillon **central du dogfooding** : sans revue KYC, aucune org (y compris Money Vibes) ne passe `APPROVED`, donc aucun module ne devient utilisable. Le backend `kyc-service` expose déjà la revue admin (STORY-013 : file, détail, URLs présignées, approve/reject 404/409). Cette story livre l'UI ; elle passe par le **BFF admin-panel** (STORY-048) quand il est prêt, sinon appelle `kyc-service` directement via la gateway avec le JWT admin.

Après décision, le backend émet `kyc.status.changed` → les read-models (app cliente, dashboard) se mettent à jour (cohérence éventuelle).

---

## Périmètre

**Inclus :**
- **File de revue** : dossiers au statut `UNDER_REVIEW` (org, date de soumission, documents) ; tri/pagination.
- **Détail d'un dossier** : métadonnées + **liens de téléchargement présignés** des pièces (RCCM/CFE), affichage/prévisualisation.
- **Actions** : **approuver** ; **rejeter + motif** (obligatoire). Confirmation + retour d'état.
- **Robustesse** : gestion 404 (dossier inconnu) et 409 (déjà décidé / re-décision) ; feedback ; rafraîchissement de la file après action (le read-model se met à jour de façon asynchrone).

**Hors périmètre :**
- Extraction OCR (assiste la revue mais backend `document-service`, plus tard) — l'humain décide (invariant DO-1).
- Octroi d'entitlement après approbation (AP-05/AP-06).

## ⚡ Concurrence optimiste des décisions — arbitrage rendu le 2026-08-07 (STORY-182)

**Issue ① retenue : le service porte la concurrence optimiste.** L'écran de conflit
(`KycConflictError`) **reste** — il n'était pas de trop, il était **en avance** : rien en
amont ne produisait le signal qu'il sait rendre. `STORY-182` le livre.

⚠️ **Ce que la revue de code a corrigé dans l'énoncé** : le `409` existait **déjà** (la
transition est conditionnelle sur `UNDER_REVIEW`), mais il était **muet**. L'écran était
inatteignable **faute de quoi le remplir**, pas faute de `409`.

### Contrat à consommer

| | |
|---|---|
| **Lecture** | `GET /admin/orgs/{orgId}` (BFF) publie `kyc.etag`. En appel direct à `kyc-service`, l'ETag est aussi en en-tête `ETag` *(exposé par CORS)*. |
| **Décision** | `POST /admin/orgs/{orgId}/kyc/approve\|reject` — en-tête **`If-Match: <etag>` OBLIGATOIRE**. |
| **`428`** | `If-Match` absent ou vide. `code: PRECONDITION_REQUISE`. **Pas une panne** : bug d'appel côté front. |
| **`409`** | L'état a bougé. `code: KYC_DECISION_CONFLIT` + `details`. |

```jsonc
// corps du 409
{
  "code": "KYC_DECISION_CONFLIT",
  "details": {
    "raison": "DECISION_CONCURRENTE",      // ou "DOSSIER_MODIFIE"
    "statutCourant": "REJECTED",
    "etagCourant": "\"471d82f1…\"",        // rejouable tel quel après relecture
    "decisionGagnante": {                   // ABSENT si raison = DOSSIER_MODIFIE
      "verdict": "REJECTED",
      "auteurUserId": "6a765d1c…",
      "dateDecision": "2026-08-07T22:35:22.962Z",
      "motifRejet": "RCCM illisible"
    }
  }
}
```

⚠️ **Les deux raisons ne se rendent PAS pareil.** `DECISION_CONCURRENTE` → « un autre
opérateur a tranché, voici qui et quand » *(l'écran existant)*. `DOSSIER_MODIFIE` →
**personne n'a tranché**, le dossier a changé sous les yeux de l'opérateur (pièce déposée,
verdict par pièce posé) : il n'y a **aucun verdict à nommer**, et afficher le message de
l'autre cas serait un mensonge. Il faut inviter à **relire**, pas annoncer une perte.

⚠️ **Les marques PAR PIÈCE ne sont pas soumises à `If-Match`** — délibéré : deux
opérateurs qui marquent deux pièces *différentes* travaillent en parallèle, ils ne sont
pas en conflit.
