## User Story

En tant que **développeur frontend de l'app cabinet**,
je veux **régénérer les types de `balance-service` et faire trancher le gate par le `code` du 403**,
afin que **les écarts que FE-024 et FE-025 avaient tracés cessent d'être des notes** —
un contrat périmé reste **vert au typecheck** tout en mentant, et un motif de refus deviné reste **faux** même
quand le serveur, lui, sait le nommer.

---

## Contexte

Trois écarts avaient été relevés à l'Integration Gate de FE-024/FE-025 et **tracés sans porteur**. Leurs
backends sont désormais livrés.

### ① Le gate devine un motif de refus sur trois — alors que le serveur le nomme (STORY-138)

FE-024 a construit `useAtelierAccess` sur une hiérarchie explicite : **l'autorité est le `code` du 403** de la
route métier gardée, et le reflet local ne sert que de repli. Mais à l'époque, le 403 « e-mail non vérifié`
sortait **sans `code`** alors que `KYC_NOT_APPROVED` et `BALANCE_NOT_ENTITLED` en portaient un — un motif sur
trois était donc **hors autorité**. Le code de `use-atelier-access.ts` porte encore ce repli :

```ts
// 2. Reflet local, dans l'ordre du backend.
if (user?.emailVerified === false) {
  return { status: "denied", reason: API_ERROR_CODES.EMAIL_NOT_VERIFIED, authoritative: false };
}
```

**STORY-138 (livrée)** a aligné le guard e-mail sur `{ message, code }` **sur les 7 relying-parties navigateur**
(auth / EC / kyc / catalog / document / bilan / balance). Le repli n'est plus la seule source : le 403 devient
**autoritaire** pour les trois motifs, et le reflet local retrouve son rôle — un confort d'affichage avant
même d'avoir appelé, jamais une conclusion.

### ② `mappingProfile` n'existe plus : c'est `profilImportId` (STORY-088)

FE-025 avait ouvert un ticket : `mappingProfile` était **déclaré dans le DTO et dans l'OpenAPI, lu nulle part**
— « un champ accepté et ignoré est un piège pour tout appelant ». FE-025 avait choisi de **ne jamais l'envoyer**
(`buildForm` l'omet volontairement). **STORY-088 a tranché l'option A** : le champ est **remplacé** par
`profilImportId` (un **identifiant**, pas un nom — « le nom d'un profil est modifiable : un import référencé par
nom cesserait de fonctionner à la première correction de libellé »).

Conséquence : `src/types/api/balance.ts` porte encore `mappingProfile?: string` (ligne ~618). **Rien n'est cassé**
— le front ne l'envoyait pas — mais le contrat généré **ment**, et FE-048 (UI de profil d'import) s'appuiera
dessus.

### ③ Des champs du contrat ne sont pas typés à l'OpenAPI

Écart n°3 de FE-024, toujours vrai : `paquetFiscal`, `stamp` et `org` sortent en `Record<string, never>` dans
les types générés — c'est-à-dire **un objet dont aucune clé n'est permise**, ce qui force à contourner par des
casts dès qu'on veut les lire.

---

## Portée

- **Régénérer** les types de `balance-service` : `npm run gen:api` (:3007) sur le **stack docker rebâti sur
  `origin/dev`**, puis **committer** `src/types/api/balance.ts` (convention FE-INT-0).
- **Rendre le gate autoritaire sur les trois motifs** dans `use-atelier-access.ts` : le `code` du 403 tranche ;
  le reflet local (`user.emailVerified`, entitlement) reste un **repli pré-appel** explicitement marqué
  `authoritative: false`. Ne pas supprimer le repli — il sert avant que la route gardée ait répondu.
- **Aligner l'import Sage sur `profilImportId`** : retirer toute trace de `mappingProfile`. FE-025 ne l'envoyait
  pas ⇒ aucune UI à changer ; il s'agit de ne pas laisser un champ mort dans les types et les commentaires.
  ⚠️ **L'UI de sélection d'un profil d'import appartient à FE-048**, pas à cette story.
- **Constater** l'état de `paquetFiscal` / `stamp` / `org` après régénération : s'ils sont typés, retirer les
  contournements ; **s'ils sortent encore en `Record<string, never>`, ouvrir un ticket backend** et le tracer
  dans `open_contract_gaps` — ne pas les re-typer à la main côté front (ce serait recréer la dette que
  FE-INT-0 a supprimée).
- **i18n / UI** : aucun écran neuf.

**Hors périmètre :** l'UI de mapping/profil d'import (**FE-048**) · le retrait du dictionnaire de saisie
(**FE-056**) · les types des autres services (auth = **FE-055**) · la validation d'état d'une balance (trou
backend `GAP-balance-validation-etat`).

## Critères d'acceptation

1. `src/types/api/balance.ts` est **régénéré depuis `:3007` en marche** (stack `origin/dev`) et committé ; le
   `git diff` montre bien `mappingProfile` **remplacé** par `profilImportId`.
2. **Aucune occurrence de `mappingProfile`** ne subsiste dans le dépôt frontend (code, types, commentaires).
3. `useAtelierAccess` traite **`EMAIL_NOT_VERIFIED` comme les deux autres motifs** : un 403 porteur du code le
   rend `authoritative: true`. Test dédié pour **chacun des trois** codes.
4. Le **repli local subsiste** et reste `authoritative: false` — test prouvant qu'il n'est utilisé que **tant
   que la route gardée n'a pas répondu** (c'est l'invariant de FE-024, ne pas le casser en le simplifiant).
5. `typecheck`, `lint`, `build` **verts** après régénération ; tests unitaires Atelier et E2E `atelier.spec` /
   `import-sage.spec` / `atelier-saisie.spec` / `atelier-balances.spec` **verts**.
6. L'état de `paquetFiscal` / `stamp` / `org` est **constaté et consigné** dans le Dev Agent Record : soit typés
   (contournements retirés), soit **ticket backend ouvert** et référencé.

## Integration Gate (DoD étendue)

1. Régénération faite contre le **service en marche**, pas contre un fichier OpenAPI copié.
2. **403 `EMAIL_NOT_VERIFIED` confronté en réel** : un compte à e-mail non vérifié appelle
   `GET /referentiels/actifs` et l'écran affiche l'orientation « vérifier l'e-mail » **sur la foi du code
   serveur**, pas du reflet — le prouver en neutralisant le reflet local dans le test.
3. Les **deux autres motifs** (`KYC_NOT_APPROVED`, `BALANCE_NOT_ENTITLED`) restent non régressés en réel.
4. **Zéro mock** sur le chemin vérifié.
