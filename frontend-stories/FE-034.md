### ✅ Maquette livrée le 2026-08-27

Un **6ᵉ onglet « Validation »** dans le module Bilan du prototype cumulatif
(`prototypes/prospera-prototype.html`). Il ne montre pas six écrans : il montre **six moments de la
MÊME liasse** — l'exercice 2025 d'Ets Kossi Distribution — dans l'ordre où ils se produisent.

| Moment | Ce qu'il rend indiscutable |
|---|---|
| Brouillon bloqué | le gate **nomme** son blocage (écart 412 300) et **n'offre pas** le bouton |
| Brouillon validable | `valide: true` ne veut pas dire « juste », et encore moins « déposable » |
| Figée v1 | plus **aucune** action d'édition ; le validateur est un `ObjectId` |
| Rouverte | la **v1 reste la seule qui fasse foi** ; aucun motif n'est demandé ni conservé |
| Figée v2 | deux versions coexistent ; l'écart v1→v2 est **soustrait par l'écran**, faute de route |
| Rouverte sur exercice clos | le **cul-de-sac** : rouvrir réussit, re-valider échoue en `409` |

**Les chiffres sont produits, pas écrits.** Un générateur construit la frise, l'historique et le
journal depuis un scénario unique, puis **assère** : l'équilibre `BZ = DZ` de chaque version figée ;
la jointure de la dernière version avec le Bilan de FE-031 (`5 700 000`) et le résultat de FE-032
(`XI = CJ = 200 000`) ; le fait que la correction v1→v2 déplace **le même montant** à l'actif et au
résultat (`+80 000`, le compte `476200` du dialogue de FE-030) ; la numérotation `1..n` sans trou ;
`count(JEU_VALIDE) == count(versions)` ; et surtout que **le journal d'un moment est un préfixe du
suivant** — c'est-à-dire qu'il est vraiment append-only.

**Piloté en navigateur avant publication** : 6 bascules vivantes (aucun slot identique à un autre),
les deux dialogues avec leurs gardes (attestation cochée, motif non vide), le `409 EXERCICE_CLOS`
joué, le filtre du journal actif, 0 erreur JS, 0 débordement, aucun SVG > 48 px, et les 8 onglets de
l'Atelier en non-régression.

**Correction apportée à l'écran voisin** : la carte du portefeuille annonçait « Liasse 2024
**déposée** » pour une liasse seulement **figée** → « Liasse 2024 **figée** » (**STORY-462**).
Et le sélecteur d'états du Bilan dit désormais **ce qu'on y lit** (brouillon vs version figée) —
cinq états y étaient anonymes.

### Ce qui est actionnable dès aujourd'hui, sans aucun backend

1. Lire une liasse **VALIDÉE** depuis `GET …/versions/:version` — **jamais** `GET …/etats/:id`.
2. Composer la liste des blocages depuis la **batterie de contrôles**, pas depuis le `422`.
3. N'offrir **aucune** action d'édition sur un jeu VALIDÉ (l'invariant est backend ; l'UI ne doit
   pas suggérer l'inverse).
4. Traiter les `409` de course comme « un collègue a validé avant vous ».
5. **Exiger une attestation cochée** avant de figer : c'est une décision d'écran (le serveur ne
   prend aucun corps), et c'est ce qui distingue un **acte** d'un clic.

## User Story

En tant que **responsable**,
je veux **valider et figer un exercice, avec un historique des versions et un journal d'audit**,
afin que **les états ne puissent plus être modifiés en douce et que chaque action soit traçable**.

---

## Contexte

Applique l'invariant d'immutabilité (l'automatisation propose, **l'humain valide**). Un jeu d'états est d'abord **BROUILLON** (recalculable) ; la **validation** est un acte humain explicite qui requiert que les contrôles bloquants passent (équilibre de la balance amont — garanti par l'Atelier FE-026/027 —, FE-030 mapping, FE-031 actif=passif, FE-033 cohérence). La validation crée un **snapshot immuable** (append-only) ; toute correction rouvre un brouillon → **nouvelle version**, l'ancienne conservée. Le **journal d'audit** trace import/mapping/validation/export.

---

## Périmètre

**Inclus :**
- **Action de validation** : gate UI qui n'autorise la validation que si les contrôles bloquants (agrégés depuis FE-033) passent ; sinon liste des blocages + orientation.
- **Confirmation explicite** (acte humain) → snapshot figé ; retour d'état (statut VALIDÉ, horodatage/validateur).
- **Historique des versions** : liste des snapshots validés d'un exercice ; consultation d'une version ; indication de la version « courante ».
- **Journal d'audit** : liste horodatée/attribuée des actions structurantes (append-only, lecture seule).
- **Ré-ouverture** pour correction → nouveau brouillon (nouvelle version à venir).

**Hors périmètre :**
- Génération des états (FE-031-B09) ; export (FE-038).
- Prévisionnel (FE-035/B12).

## Critères d'acceptation

- [ ] **AC-1** — Validation impossible tant que des contrôles bloquants échouent ; blocages listés + orientation.
      ⚠️ **Amendé** : la liste des blocages se compose depuis la **batterie de contrôles** (FE-033), **jamais** depuis
      le refus `422` — celui-ci ne renvoie que des chaînes `« CODE : STATUT (écart N) »`, sans libellé ni cible. Le
      `422` est un **garde-fou de dernière seconde**, pas une source d'affichage.
- [ ] **AC-2** — Validation = acte humain confirmé → snapshot figé ; statut VALIDÉ + horodatage affichés ; l'état
      validé n'est plus recalculable (lecture seule).
      ⛔ **Le « validateur » n'est pas servable** : `SnapshotSommaireDto.validePar` est un `ObjectId` nu et aucune
      route ne le résout en nom → **STORY-457**. L'écran affiche l'identifiant tel quel, marqué comme non résolu.
- [ ] **AC-3** — Historique des versions consultable ; version courante identifiée ; ré-ouverture → nouveau brouillon.
      ⚠️ Une réouverture **conserve** le numéro de la dernière version figée (`rouvrir()` le dit explicitement) :
      l'écran doit annoncer « v2 reste la seule qui fasse foi », pas « aucune version ».
- [ ] **AC-4** — Journal d'audit affiché (append-only, lecture seule) : action, **auteur**, horodatage, cible.
      ⛔ **INAPPLICABLE EN L'ÉTAT** — `userId` est un `ObjectId` nu (**STORY-457**), le `contexte` n'est pas publié
      (**STORY-458**), et les **surcharges de mapping ne sont pas journalisées** (**STORY-467**) alors que la fiche
      demande de tracer « import/mapping/validation/export » : **deux sur quatre** sont servis.
- [ ] **AC-5** — i18n FR ; tests : gate de validation (bloqué/ok), figement (lecture seule), versions, audit.
- [ ] **AC-6 (nouveau)** — Une liasse **VALIDÉE** est lue depuis `GET …/versions/:version`, **jamais** depuis
      `GET …/etats/:id`, qui la **re-calcule** (**STORY-465**). Le test le garde explicitement : aucun appel à
      `GET /etats/:id` sur un jeu dont le statut est `VALIDE`.
- [ ] **AC-7 (nouveau)** — Les conflits de course (`409 JEU_DEJA_VALIDE`, `409 SNAPSHOT_VERSION_CONFLICT`) sont
      traités comme **« un collègue a validé avant vous »** : rechargement + affichage de la version créée, jamais
      un message d'erreur technique.
