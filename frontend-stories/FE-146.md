## Le constat (gate de FE-069, 2026-11-18)

Un dossier neuf doit **décider ses axes** (système comptable SN/SMT, régime fiscal) avant que l'Atelier traite ses
comptes. La décision s'écrit dans `dossier-service`. `balance-service` la reçoit **par Kafka** : topic
`dossier.axes.decides`, lu par `src/modules/read-models/axes-consumer.bootstrap.ts`.

Pendant les quelques secondes de propagation, toute lecture ou écriture de l'Atelier sur ce dossier répond :

> `409 SYSTEME_COMPTABLE_INDETERMINE` — « Aucun système comptable n'est déterminé pour le dossier … : renseigner les
> axes du dossier avant de traiter ses comptes. »

Le gate l'a rencontré **de façon intermittente**, juste après la décision et sur l'analyse d'un import Sage. Pour
l'utilisateur, le message est **faux** : il vient précisément de décider les axes. Il l'envoie refaire un geste déjà
fait, alors qu'il suffit d'attendre quelques secondes. Le refus disparaît seul.

## User Story

**En tant qu'**expert-comptable qui vient de décider les axes d'un dossier,
**je veux** que l'Atelier attende leur arrivée et me le dise, au lieu de m'annoncer qu'aucun système comptable n'est
déterminé,
**afin de** ne pas refaire une décision déjà prise, ni croire à une panne.

## Périmètre

**DANS le périmètre** : le front seul.

1. Distinguer **deux cas** derrière le même `409 SYSTEME_COMPTABLE_INDETERMINE` de `balance-service`, en lisant les
   axes du dossier dans `dossier-service` (`GET /dossiers/{id}/axes`, déjà servi, déjà lu par FE-065) :
   - **les axes sont décidés** côté `dossier-service` ⇒ c'est une **propagation en cours** ;
   - **les axes ne sont pas décidés** ⇒ le message actuel reste juste, avec le lien vers l'onglet « Les 2 axes » de la
     fiche.
2. **Propagation en cours** : l'écran le dit (« Les axes viennent d'être décidés ; l'Atelier les reçoit. Nouvel essai
   dans quelques secondes. ») et **rejoue la lecture** de lui-même, avec un délai croissant et une borne (au plus une
   vingtaine de secondes). Au-delà, il le dit et propose de réessayer, sans renvoyer décider les axes.
3. **Écritures** (analyse ou enregistrement d'un import, saisie directe, cahiers) : **aucun rejeu automatique**.
   L'écran dit la propagation et garde le bouton. Rejouer une écriture à la place de l'utilisateur n'est pas un geste
   anodin, même quand elle est un aperçu.
4. Écrans concernés : la carte du référentiel (`referentiel-card.tsx`), le refus des cahiers (`cahier-refus.ts` et
   `cahier-refus-alerte.tsx`), l'import Sage et la saisie directe. Le texte vit dans `fr.json`.

**HORS périmètre** :

- Tout changement de `balance-service`. Une autre voie existe : `balance-service` pourrait lire les axes de façon
  synchrone, ou rendre un code distinct pour « décision connue, pas encore reçue ». Elle relève d'une story backend du
  groupe qui tient balance (B pour le lot 4), si le PO la préfère un jour. Cette story ne la bloque pas.

## Critères d'acceptation

**AC-1** — Après la décision des axes, une **lecture** de l'Atelier refusée par `409 SYSTEME_COMPTABLE_INDETERMINE`
affiche le message de propagation (jamais « renseigner les axes ») et aboutit **sans geste de l'utilisateur** dès que
`balance-service` répond.

**AC-2** — Quand les axes ne sont **pas** décidés dans `dossier-service`, le message actuel et le lien vers « Les 2 axes »
restent inchangés.

**AC-3** — Une **écriture** refusée pendant la propagation dit la propagation et n'est jamais rejouée automatiquement.

**AC-4** — Le rejeu est **borné** (une vingtaine de secondes au plus). Au-delà, l'écran le dit et propose de réessayer.

**AC-5** — Tests :
- unitaires : la classification des deux cas (axes décidés ou non × code reçu) ;
- e2e simulé : un premier `409`, puis `200`, puis l'aperçu affiché sans clic ;
- **gate réel** (`e2e/gate/parcours-cabinet-dossier.spec.ts`) : la boucle de réessai ajoutée par FE-069 autour de
  « Analyser » est **retirée**, et le parcours reste vert.
