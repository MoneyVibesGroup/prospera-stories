## User Story

En tant qu'**équipe**,
je veux **un test automatisé qui prouve qu'un octroi fait dans la console admin allume réellement le module dans l'app cliente**,
afin de **ne jamais casser en silence la boucle qui justifie toute notre topologie**.

---

## Contexte

**C'est la story qui rend le principe 0 exécutable.** Le sprint 5 livre les deux moitiés d'une même
preuve : l'admin octroie (AP-05), le client s'allume (FE-014). Chacune, seule, est indémontrable — et
surtout, **rien ne garantit qu'elles restent connectées** après un refactor de l'une ou de l'autre.

C'est le **miroir frontend** du `npm run test:chain` backend (STORY-049), qui a fait passer la chaîne KYC
du statut « ça a marché une fois en démo » à « c'est prouvé rejouable ». La même logique s'applique ici :
la boucle entitlement est le cœur du dogfooding **DG-1** (l'entitlement est octroyé **manuellement** via
l'admin-panel tant que le paiement n'existe pas, sprint 16) et de la topologie **Option B** (une seule app
cliente config-driven qui n'affiche que les modules actifs).

Sans ce test, la première régression silencieuse se découvre chez le client zéro — c'est-à-dire nous.

---

## Portée

**Playwright, contre le stack docker réel** (`docker compose up`, 4 services + mongo/kafka), pas de mock.

Scénario nominal :

1. **Arrange** — une org cabinet KYC-approuvée, **sans** l'entitlement `bilan` (état de départ explicite,
   pas hérité d'un test précédent).
2. **Client** : se connecter en `TENANT_ADMIN` → le module n'apparaît **pas** dans la home des modules.
3. **Admin** : se connecter en `PLATFORM_ADMIN` → octroyer l'entitlement `bilan@<version>` à cette org.
4. **Propagation** : `entitlement.changed` (outbox → Kafka, clé `orgId`, état **absolu**).
5. **Client** : recharger → le module `bilan` **apparaît**.
6. **Révocation** : l'admin révoque (soft → `REVOKED`) → le module **disparaît** côté client.

⚠️ **Le piège à traiter, pas à ignorer : la propagation est ASYNCHRONE.** Le grant est synchrone côté
catalog, mais la diffusion passe par l'outbox relay (`relayIntervalMs` ≈ 2 s) puis Kafka. Un
`waitForTimeout` arbitraire rendra ce test **instable** — c'est la façon la plus sûre de le faire
désactiver dans trois sprints. Utiliser une attente **sur condition** (polling de l'UI / de
`GET /catalog/entitlements/:orgId` jusqu'à convergence, avec timeout généreux et message d'échec clair).

---

## Critères d'acceptation

1. Le test s'exécute contre le stack docker réel, **sans aucun mock**, et est **rejouable** (état de
   départ construit par le test, pas supposé).
2. Il échoue de façon **lisible** si la boucle casse (message qui dit quelle étape n'a pas convergé).
3. Il couvre l'octroi **et** la révocation (l'état absolu de `entitlement.changed` marche dans les 2 sens).
4. Aucune attente fixe arbitraire : l'attente porte sur une **condition**.
5. Il est câblé dans un script npm dédié (miroir de `test:chain`) et documenté en une ligne dans le README.
6. Il ne dépend pas de données résiduelles d'un run précédent (idempotent).

## Note

## Ce que le test a trouvé (2026-08-09)

### ⛔ 1. La console ne pouvait PLUS octroyer — corrigé ici

`toCatalogModule()` **jetait `referentielFamilies`**, sur la foi d'un écart d'Integration Gate
(« n'existe pas amont ») devenu faux : **STORY-148 est livrée**, le service sert le champ
(`balance → ["syscohada-revise"]`) et l'OpenAPI le déclare. Conséquence en chaîne :
`requiresReferentiel()` faux pour **tous** les modules → le formulaire annonçait « ne consomme aucun
référentiel normatif », n'offrait aucun sélecteur, envoyait un `PUT` sans référentiel → **400
`REFERENTIEL_REQUIRED`**. **`balance` est le seul module octroyable du catalogue : l'octroi était donc
mort dans la console.** Second symptôme du même défaut : faute de familles, l'écran avertissait sur
l'empreinte d'un `ap12-e2e` qu'il n'allait de toute façon pas envoyer, tout en disant n'en vouloir aucun.

**Aucun test unitaire ne pouvait le voir** : ils décrivent tous des modules **avec** leurs familles
(`fixtures.ts`). Corrigé dans cette story parce que c'est exactement le chemin que la boucle protège.
⚠️ `provisioning/plan.ts` portait la même affirmation périmée — commentaire corrigé, **comportement
inchangé** (bloquer large reste le bon choix pour un octroi en série ; affiner est un travail d'AP-06).

### ⛔ 2. `If-Match` est obligatoire sur la décision KYC — et la console ne l'envoie pas

**STORY-182 est livrée** : `approve`/`reject` exigent l'ETag du dossier en `If-Match`, sinon **428
`PRECONDITION_REQUISE`** (reproduit au curl). Or `kyc-client.ts` (`submitDecision`, `rejectFile`)
n'envoie **aucun** `If-Match` — les types générés le déclarent pourtant obligatoire.
⇒ **la revue KYC de la console ne peut plus rien approuver ni rejeter**, et `kyc-chain.spec.ts` (le
jalon 🏁 du S4) est rouge. **Hors périmètre de FE-017** — c'est le sujet d'AP-INT-2 : une story
frontend à ouvrir ou à y rattacher. Le présent test approuve donc par API, avec l'ETag relu **après**
les marques.

### ⚠️ 3. `kyc-chain.spec.ts` vise MailHog sur `:8025`

Le compose racine décale MailHog en **`8026`** (Mailpit de Laragon occupe 8025 sur les postes Windows).
Le défaut de ce spec n'a pas été corrigé — il tombe de toute façon sur le point 2, et le réparer à
moitié cacherait le vrai problème. À solder avec lui.

### ⚠️ 4. « Identifiants invalides » recouvre TOUTES les erreurs d'API

`login-form.tsx` (les **deux** apps) rend `t("invalidCredentials")` pour tout `ApiError` : un **429**
de quota s'affiche donc comme un mauvais mot de passe, et l'utilisateur va réinitialiser un mot de
passe qui n'a rien. Même famille que la trouvaille d'AP-09 (« un mauvais tri fait perdre un jeton
valide »). Coûté ~30 min de diagnostic ici, avec l'IdP répondant **200 neuf fois sur neuf** dans ses
journaux pendant que l'écran annonçait des identifiants invalides. Le test capte désormais le **statut
réel** de `POST /api/auth/login` et le met dans son message d'échec. **À traiter dans une story.**

### ⚠️ 5. Le quota de l'IdP est GLOBAL par IP, et un e2e navigateur le mange

`THROTTLE_LIMIT`/`THROTTLE_TTL` = **100 requêtes / 60 s par IP**, pas par compte ni par route. Une
attente sur condition qui recharge la page toutes les secondes épuise ce budget et fait échouer la
**connexion de l'exécution suivante**. Traité : cadence de sondage espacée (2/5/10 s — largement plus
fine que la propagation) et réessai unique **après une fenêtre entière** sur 429.

### ⚠️ 6. Le `.env.local` de l'app cabinet pointe une IP de LAN injoignable

`10.199.13.113` (celui de la console dit `10.169.144.113` : les deux ne peuvent pas être vrais en même
temps). Les `NEXT_PUBLIC_*` étant inlinées **au build**, un build repris tel quel produit une app dont
tous les appels échouent. La configuration de la boucle **impose `localhost`** aux deux builds et ne
touche pas les fichiers du développeur. C'est le même écart d'environnement qu'AP-09 avait signalé ;
il reste à trancher (deux profils d'env, ou une IP joignable des deux côtés).

## Ce que le test couvre réellement

**Deux pattes, de natures différentes — et c'est le point.** L'accueil du cabinet lit
`GET /catalog/entitlements/:orgId` **en direct** : il reflète l'octroi presque aussitôt, ce n'est que
l'écho de l'écriture qu'on vient de faire. La preuve de la **propagation**, c'est l'**entrée dans le
module** : `/referentiels/actifs` est gardée par `@RequiresBalanceAccess`, qui lit le read-model
alimenté par Kafka. Un test qui s'arrêterait à la carte de l'accueil resterait **vert avec la chaîne
d'événements morte**. Les deux sont vérifiées, à l'octroi comme à la révocation.
