## User Story

En tant qu'**administrateur plateforme Money Vibes**,
je veux **créer un projet rattaché à une organisation et y regrouper des modules**,
afin de **décrire ce qu'un client déploie réellement, au-delà de la liste plate de ses droits d'usage**.

---

## Contexte

Un **projet appartient à une organisation et regroupe des modules** (cadrage PO). C'est une couche
d'**organisation du périmètre client**, au-dessus des entitlements qui, eux, restent l'autorité sur
ce qui est autorisé.

**La règle qui structure l'écran, posée par STORY-141 :** un projet ne peut référencer que des
modules **déjà entitlés `ACTIVE`** pour son organisation. L'UI doit rendre cette règle évidente
*avant* le refus, pas la subir : le sélecteur de modules ne propose que les modules entitlés de
l'org choisie, et explique l'absence des autres. Un module dont l'entitlement est révoqué après coup
reste attaché mais s'affiche **dégradé** — le backend ne cascade pas la suppression, l'admin tranche.

**Où l'onglet se place.** Le catalogue (AP-04) a aujourd'hui trois onglets : Modules · Versions ·
Référentiels. Projets devient le **quatrième**, à côté de Référentiels. C'est cohérent : ces quatre
onglets décrivent l'offre et son organisation ; ils n'octroient rien (l'octroi est AP-05).

---

## Périmètre

**Inclus :**
- **Onglet « Projets »** dans le catalogue, à côté de Référentiels : liste des projets avec
  organisation propriétaire, nombre de modules, statut (`ACTIVE` / `ARCHIVED`).
- **Filtre par organisation** — c'est l'axe de lecture naturel d'un projet.
- **Créer un projet** : organisation (obligatoire), nom, description ; modules facultatifs à la
  création.
- **Détail d'un projet** : ses modules avec, pour chacun, la **version entitlée** et le statut de
  l'entitlement.
- **Ajouter des modules** : sélecteur limité aux modules **entitlés `ACTIVE`** de l'organisation, avec
  une explication quand la liste est vide (« cette organisation n'a aucun module actif — commencez
  par lui en octroyer un », lien vers AP-05).
- **Retirer un module** d'un projet.
- **Archiver** un projet (pas de suppression — les projets sont référencés par l'historique client).
- **Module dégradé** : entitlement révoqué après attachement → ligne signalée, avec ce que ça
  implique et le geste de sortie (retirer le module, ou re-octroyer via AP-05).

**Hors périmètre :**
- Octroyer un entitlement depuis cette vue → **AP-05**.
- Jalons, budget, affectation de collaborateurs à un projet.
- Vue projet côté client (app expert-comptable).

## Critères d'acceptation

- [ ] L'onglet « Projets » apparaît dans le catalogue à côté de Référentiels, sans casser les trois existants.
- [ ] La liste affiche organisation, nom, nombre de modules et statut ; le filtre par organisation fonctionne.
- [ ] Créer un projet rattaché à une organisation → il apparaît dans la liste.
- [ ] Le sélecteur de modules ne propose **que** des modules entitlés `ACTIVE` de l'organisation choisie.
- [ ] Deux projets de même nom dans la même organisation → **409** relayé et affiché de façon compréhensible.
- [ ] Le détail d'un projet affiche la **version entitlée** de chaque module.
- [ ] Un module dont l'entitlement est révoqué s'affiche **dégradé**, avec le geste de sortie proposé.
- [ ] Ajouter / retirer un module est reflété ; ajouter deux fois le même module est sans effet.
- [ ] Archiver un projet le passe en `ARCHIVED` ; aucune action « supprimer » n'est exposée.
- [ ] Un acteur sans `project:manage` voit la liste (si `project:read`) mais aucune action d'écriture (masquage `perms[]`, patron AP-08).
- [ ] i18n FR ; tests : liste, création, validation catalogue/entitlement, module dégradé, archivage, gating par permission.
