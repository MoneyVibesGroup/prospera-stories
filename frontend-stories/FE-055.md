## User Story

En tant que **développeur frontend de l'app cabinet**,
je veux **regénérer les types TS depuis l'OpenAPI corrigé de l'IdP et corriger les types dérivés faux**,
afin que **le front cesse de propager silencieusement les descriptions erronées que STORY-130 vient de réparer** —
un contrat faux côté serveur devient un **type faux** côté client, et le front dérive ses types de cet OpenAPI.

---

## Contexte

Le front **dérive ses types de l'OpenAPI de chaque service** (décision FE-INT-0 : `gen:api` = un fichier par
service sous `src/types/api/`, committés). Tant que l'OpenAPI de l'IdP **décrivait mal ses réponses**, ces
types générés étaient **faux mais verts** — la dette était invisible.

**STORY-130 (livrée) a corrigé 5 écarts** confrontés aux réponses réelles :
1. `GET /users/me` → champ `organization` passait de `{"type":"object"}` **opaque** à un `$ref OrganizationInfo`
   **nullable** — avant, le front voyait un `object` informe et devait deviner la forme (ou avait un type écrit à
   la main qui dérivait).
2. **6 routes** renvoyaient `{ message }` avec `content: never` → désormais `MessageResponseDto` partagé (un client
   généré strict traitait le corps comme **inexistant**).
3. `POST /auth/forgot-password` **déclarait 200** alors qu'il répond **202** (`@HttpCode(ACCEPTED)`) → un client
   généré strict traitait une réponse **normale comme un échec**.
4. `POST /auth/verify-email` : le 200 portait `content: never` alors qu'il renvoie `{ message }` (déjà tracé
   comme écart backend par **FE-INT-4** — c'est la même dette, maintenant réparée à la source).
5. **BONUS** : `GET /.well-known/jwks.json` renvoyait son corps **sans aucune déclaration** → désormais
   `JwksResponseDto`/`JwkDto` (l'ancre de confiance RS256).

Cette story est le **retrofit côté front** : régénérer, puis **supprimer les contournements** (types manuels,
casts, hypothèses `keys[0]`, gestion d'un forgot-password « en échec sur 202 ») que la dette avait imposés.

---

## Portée

- **Régénérer** les types de l'IdP : `npm run gen:api` (auth-service :3001) sur le **stack docker réel** rebâti
  sur `origin/dev` (l'OpenAPI servi doit inclure les correctifs STORY-130 — vérifier que le conteneur exécute
  bien la branche à jour, piège récurrent des checkouts périmés).
- **Committer** les fichiers `src/types/api/` régénérés (convention FE-INT-0).
- **Corriger les types dérivés** dans les features qui consommaient les surfaces re-décrites :
  - `organization` sur `/users/me` : consommer le `OrganizationInfo | null` généré, retirer tout type local ou
    cast qui suppléait le `object` opaque (features `auth` / `users` / shell — cf. FE-015 qui lit l'identité).
  - Réponses `{ message }` : les endpoints publics (verify-email, forgot-password, reset-password…) peuvent
    désormais **lire le corps** au lieu de le supposer vide.
  - `forgot-password` : aligner le code de succès attendu sur **202** (retirer tout traitement d'un 200/erreur).
  - JWKS : si un utilitaire côté front le lit, ne **jamais** supposer `keys[0]` — plusieurs clés à la fois est le
    cas **normal** (rotation). *(Le plus souvent le front ne lit pas JWKS ; ne rien inventer si aucun code ne le
    consomme — se contenter du type généré.)*
- **i18n / UI** : aucun nouvel écran. Pur alignement de contrat.

**Hors périmètre :** toute nouvelle fonctionnalité · les 7 autres services (STORY-130 ne touche que l'IdP ; leur
test de contrat OpenAPI est un patron transposable, pas cette story) · re-génération opportuniste de services
non touchés.

## Critères d'acceptation

1. `src/types/api/` de l'auth-service est **régénéré depuis l'OpenAPI corrigé** (STORY-130) et committé ; le
   `git diff` sur ces fichiers reflète bien les 5 correctifs (organization `$ref` nullable, `MessageResponseDto`,
   202 forgot-password, verify-email `{message}`, `JwksResponseDto`).
2. **Aucun type manuel ni cast** ne subsiste pour combler le `organization` opaque ou les corps `{ message }` :
   la garde de compilation passe par les **types générés** (un renommage backend re-casse le typecheck).
3. `forgot-password` est traité comme **202** partout où il est appelé (aucun chemin ne le voit comme un échec).
4. `typecheck`, `lint`, `build` **verts** après régénération (le diff de types ne casse aucune surface).
5. Tests existants **verts** ; ajouter/ajuster un test là où un type dérivé faux était compensé par un mock
   (ex. la forme de `organization` sur `/users/me` — angle mort si le test mockait le hook entier, cf. leçon
   FE-INT-4).
6. Si du code front lit JWKS : test prouvant qu'il **n'assume pas `keys[0]`** ; sinon, note explicite « aucun
   consommateur front de JWKS » dans le Dev Agent Record.

### ⚡ Le constat qui redéfinit la story : la régénération était **déjà faite**, le retrofit non

`npm run gen:api -- auth` rejoué contre le conteneur vivant (`:3001`, 37 chemins, OpenAPI portant bien
les 5 correctifs de STORY-130 **et** celui de STORY-132) : **zéro diff**. `src/types/api/auth.ts` sur
`origin/dev` était déjà à jour — **FE-INT-5** l'avait régénéré au passage le 2026-08-18, en même temps
que `dossier.ts`.

⛔ **L'AC-1 est donc, à la lettre, inatteignable** : aucun `git diff` sur les types ne peut « refléter les
5 correctifs », ils sont entrés dans le dépôt il y a deux jours. Ce qu'il faut lire dans ce zéro n'est
pas « rien à faire » mais l'inverse :

> **Une régénération de types faite en passager clandestin d'une autre story met les types à jour
> SANS retirer un seul des contournements qu'ils rendent caducs.** Le contrat était réparé côté fichier
> généré, et le front continuait de le contourner partout — invisiblement, et *en vert*.

C'est exactement le mode de panne que la note « ⚠️ piège des checkouts périmés » de la story anticipait,
retourné : le piège n'a pas été de régénérer trop tard, mais d'avoir régénéré **trop tôt et pour autre
chose**. ⇒ **Règle : une régénération large ne se glisse pas dans une story qui consomme un champ** —
c'est précisément ce que le garde-fou de `gen-api.mjs` (FE-070, régénération CIBLÉE) impose depuis, et
`auth` avait échappé à cette règle d'un jour.

## Suite — le « à constater » de STORY-133, vérifié en vrai navigateur (2026-08-21)

Le Dev Agent Record ci-dessus laissait ce point **ouvert et non vérifié**. Il l'est maintenant, et il
**échoue** — pour une cause qui n'est ni FE-055 ni STORY-133.

**Méthode** : vrai Chromium, connexion avec les identifiants de démo **via le BFF**, puis lecture de la
carte « Sessions ouvertes » à l'écran. Un `curl` ne pouvait pas répondre : il mesure le chemin qu'il
emprunte lui-même et ne passe jamais par le BFF.

```
Chrome 149 sur Windows        172.22.0.1     ← navigateur, via le BFF
Playwright/1.61.1 … node/25.2 172.22.0.1     ← client API, en direct
```

`172.22.0.1` est la **passerelle du pont docker**. Toutes les sessions portent la même IP quel que soit
le chemin : l'écran affiche une adresse qui **ne distingue aucun appareil**, ce qui rend le repère
« lieu inhabituel » de FE-021 inexploitable.

⚡ **Le `User-Agent` est correct**, lui — « Chrome 149 sur Windows », plus « node ». Le correctif de
FE-021 tient en navigateur. **Seule l'IP reste fausse.**

**Deux maillons manquants, aucun dans STORY-133** *(qui est `done` et correcte — elle a livré la
serrure)* : ① le BFF n'envoie pas `X-Forwarded-For` (`idpHeaders()` ne reporte que le `User-Agent`) ;
② `TRUSTED_PROXIES` est vide dans le stack, donc l'IdP ignorerait l'en-tête même s'il arrivait.

⛔ **Et la raison pour laquelle personne ne l'avait branché tient en un commentaire** : le docstring
d'`idpHeaders()` affirmait encore que « l'IP ne peut PAS être corrigée d'ici ». Vrai jusqu'au
2026-08-06, faux depuis. **Un commentaire d'écart périmé déclare le travail impossible, donc personne
ne l'entreprend** — même forme que la leçon de FE-017, et deuxième occurrence dans cette seule story
*(la première étant le commentaire d'écart de `get-current-user.ts`)*. ⇒ **Règle : quand une story
backend passe `done`, balayer les commentaires front qui décrivaient son absence.**

⇒ Commentaire corrigé ici *(commit `7663aeb`)* ; le travail lui-même est **FE-072** *(3 pts, `blocked` —
il exige un arbitrage de déploiement sur `TRUSTED_PROXIES`, et ne doit pas être livré seul : croire un
`X-Forwarded-For` sans borner le proxy de confiance est une **usurpation d'IP**)*.

⚠️ **Deux pièges rencontrés pendant la vérification, qui valent pour la prochaine** :
- Le serveur de `:3100` tournait sur un build que `npm run build` avait remplacé sous ses pieds ⇒
  chunks en **500** et page blanche « This page couldn't load ». Ce n'était **pas** un bug produit, et
  ça en avait tout l'air. ⇒ après un `build`, **redémarrer le `next start`** avant toute lecture
  d'écran. *(Contourné sans tuer le processus existant : `:3110` est la seconde origine autorisée par
  `CORS_ALLOWED_ORIGINS` — utile à savoir, un autre port aurait échoué au CORS.)*
- Un `waitForURL` posé **après** le clic rate la navigation quand la connexion est rapide : attendre la
  **réponse** `/api/auth/login` avant la navigation. Le symptôme (« timeout ») se lit comme un échec de
  connexion, alors que le HTTP était **200**.
