## Pourquoi

Les packs de chaque métier existent **en deux copies** : la console les code en dur (`provisioning/config/vertical-packs.ts`) et le catalogue en garde une copie (`packs.front-snapshot.ts`) : **deux copies, aucune source**. Chaque fois que le catalogue change, la console dérive (AP-36, AP-37, AP-54 A3 et A4 en sont nés). Par ailleurs le formulaire de version n'envoie pas de **manifeste** (dépendances, droits, vérifications), qui est optionnel : l'opérateur ne peut pas le publier depuis la console.

## Ce qui est attendu

- **Packs** : la console **lit** les packs au catalogue ; plus de liste en dur. Un changement de pack se fait au catalogue (créer, modifier, retirer) et la console le suit sans republication.
- **Manifeste** : le formulaire d'une version accepte le manifeste en **déposant le fichier** (rien à saisir à la main), vérifié avant l'envoi ; le tiroir d'un module affiche ses dépendances **avec leur raison**.
- Les refus `MANIFESTE_*` se disent en phrase, sans code, avec ce qu'il faut corriger.
- L'opérateur ne voit que le résultat : « pack Distribution : 6 modules ».

## Critères d'acceptation

- **AC-1** : `vertical-packs.ts` ne contient plus de liste ; le plan de l'assistant de provisioning lit `GET /catalog/packs`.
- **AC-2** : une version se publie avec son manifeste déposé en un geste ; un manifeste invalide est refusé avec une phrase claire.
- **AC-3** : la fiche d'un module montre ses dépendances et leur raison.
- **AC-4** : la table `MODULE_DEPENDENCIES` d'AP-54 disparaît au profit des manifestes lus.
- **AC-5** : maquette validée avant le code ; `tsc`, lint, Vitest, build verts ; le gate de provisioning reste vert sur la vraie pile.
